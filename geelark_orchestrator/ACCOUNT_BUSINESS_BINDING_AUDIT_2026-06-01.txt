CONCLUSION: ACCOUNT-BUSINESS BINDING
================================================================================

LAYER 1 (API / Desktop browser):  ONE-TO-MANY
    - account["target_businesses"] = ["biz_001", "biz_002", ...]
    - An account can be assigned multiple businesses via the /assign-group endpoint
    - The account warmer desktop code selects from target_businesses at runtime

LAYER 2 (CSV / Geelark RPA):       ONE-TO-ONE
    - Each CSV row has exactly one business_name
    - The resolver passes it straight to RunPlan
    - No pool, no random selection, no fallback

ANSWER: Each account has ONE fixed associated business in the Geelark
pipeline (1:1 from CSV). The desktop browser pipeline supports multiple
businesses per account (1:many via target_businesses), but the Geelark
RPA pipeline does not use this.

================================================================================

ANSWER: It is ALWAYS the same one per account — hardcoded in the CSV.

The name "The Dickens Inn" comes from:
  1. The CSV file (goal_a6_y77.csv, etc.)
  2. Loaded via data_adapter.profile_from_real_csv_row()
  3. Passed through resolver → RunPlan.business_name
  4. Baked into the Maps flow template via maps_flow_baker.py:

     FILE: geelark_orchestrator/src/maps_flow_baker.py (lines 118-120)
        baked_gal_str = gal_str.replace(HARDCODED_SEARCH, search_term)
        baked_gal_str = baked_gal_str.replace(HARDCODED_BUSINESS, business_name)

     The template JSON has a hardcoded literal like "Sidcup Plumbing & Heating"

you must edit the CSV or generate a new one.

     - retail:     ["supermarket near me", "hardware store near me", ...]

  2. For each session, it picks a random category term (e.g. "pub near me")

  3. It collects result elements and browses 1-3 RANDOM listings:

4. CAN THE MAPS FLOW BE LOOPED FOR MULTIPLE BUSINESSES?
================================================================================

SHORT ANSWER: Not in the current architecture. Each business requires a
separate flow dispatch (or a fundamentally different flow design).

REASONS:

  A. The flow template is built around ONE business_name literal.
     The maps_flow_baker.py does a single string replacement:
       gal_str.replace(HARDCODED_BUSINESS, business_name)
     The template has ONE "click business" step, not a loop.

  B. The Geelark RPA flow format has forTimes loops but no "for each item
     in list" construct that would allow iterating over multiple businesses
     within one flow.

  C. The _ui_clear_storage() and GPS setup steps are designed for one run.
     Repeating them inside a loop would be inefficient and fragile.

  D. The evidence collector (maps_evidence.py) checks for ONE business_name
     on screen. It has no concept of "find business A, then business B."

WORKAROUND: Dispatch multiple flows sequentially
    - Run flow for business 1 → poll → verify
    - Rotate proxy (optional)
    - Run flow for business 2 → poll → verify
    - etc.
    This is what the batch runner already does, but each account gets one
    business per CSV. To do multiple businesses per account, you'd need
    multiple CSV rows (same account_id, different business_name) or a loop
    in the Python orchestrator.

5. WHAT WOULD NEED TO CHANGE FOR MULTI-BUSINESS SEQUENCE?
================================================================================

DESIRED SEQUENCE:
    "Open Maps → interact with 2-3 random nearby businesses → then interact
    with the associated business"

CHANGES REQUIRED:

5A. DATA LAYER
    - Add a "nearby_businesses" pool to the Profile dataclass (similar to
      nearby_points but for business names)
    - Load it from CSV or from maps_data.json search_categories
    - Example: nearby_businesses: ["The Crown", "The Anchor", "The Red Lion"]

5B. RESOLVER
    - Add a "warmup_businesses" field to RunPlan
    - Select 2-3 random items from nearby_businesses pool
    - Keep the primary "business_name" as the final target

5C. FLOW BUILDER (run_full_maps_flow.py)
    - Replace the single "click business" + "interact" block with a LOOP:

      for warmup_biz in run_plan.warmup_businesses:
          fb.click("text", warmup_biz, search_time_ms=8000)
          fb.wait(3000)
          # Optional: scroll + interact with warmup business (light)
          fb.scroll_down(min_px=300, max_px=500)
          fb.click("text", "Save", search_time_ms=5000, error_type="skip")
          fb.press_back()  # return to results

      # THEN the primary business
      fb.click("text", profile.business_name, search_time_ms=8000)
      fb.wait_for_element("text", profile.business_name, search_time_ms=8000)
      # Full interaction sequence (Phases 1-3)

    - Add "back" steps between businesses to return to the search results list
    - Add a "Search here" re-tap if returning to results doesn't work

5D. EVIDENCE COLLECTOR (maps_evidence.py)
    - Modify to check for MULTIPLE business names on screen, not just one
    - Track which businesses were found vs. not found
    - Report: warmup_found=["The Crown", "The Anchor"], primary_found="The Dickens Inn"

5E. FLOW TEMPLATE
    - The .maps_flow_template.json would need to be restructured to support
      a loop (forTimes in Geelark GAL), or the Python builder would need to
      generate repeated search→find→interact blocks for each business.

5F. PROXY / GPS
    - Currently proxy rotates BETWEEN runs (one rotation per phone).
    - For multi-business per session, you'd need proxy rotation BETWEEN
      businesses, or accept that all businesses in one session share the
      same IP (which may be fine for warm-up businesses).
    - GPS stays the same for all businesses in one session (same location).

5G. STATE TRACKING
    - Add a "visited_businesses" list to the per-account state (SQLite or JSON)
    - Avoid repeating the same nearby business across sessions
    - This is already done in the desktop maps.py (_record_visit), but not
      in the Geelark pipeline.

ESTIMATED COMPLEXITY:
    - Data layer: Low (add one field to Profile)
    - Resolver: Low (random selection from pool)
    - Flow builder: Medium (loop structure, back navigation)
    - Evidence: Medium (multi-business matching)
    - Template: High (requires rebuilding the Geelark flow JSON template)

ALTERNATIVE (Simpler):
    Instead of multi-business within one flow, run SHORT warm-up flows
    before the primary flow:
      1. Dispatch "Maps browse" flow (random category, click 1-2 listings)
      2. Dispatch "Primary business" flow (The Dickens Inn, full interactions)
    This requires two Geelark tasks per phone but keeps the flow templates
    simple and the evidence per-run clean.
